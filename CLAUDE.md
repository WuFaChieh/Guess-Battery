## Architecture

**Stack**: React 18 + TypeScript + Vite, Tailwind for styling, Framer Motion for animation, `@supabase/supabase-js` for realtime PK matchmaking, `canvas-confetti` for celebration effects, `lucide-react` for icons, `@capacitor/*` for the native iOS shell. No router — the whole app is a single page with client-side mode switching.

### Dual target: website + native iOS app, developed in parallel

This is one React codebase shipped two ways, and **both are actively maintained — neither is a fallback for the other**:

- **Web**: deployed to Vercel (`vercel.json` rewrites everything to `index.html` for SPA routing).
- **iOS**: the same `dist/` build wrapped by Capacitor (`capacitor.config.ts`) into the native project under `ios/App`. `npm run cap:sync` rebuilds `dist/` and copies it into the native shell.

The dev machine for this project is Windows, which cannot open or build the Xcode project at all — there is no local way to verify the iOS side. Two things exist specifically to cover that gap:

- `.github/workflows/ios-build.yml` builds the iOS app (unsigned, for the Simulator) on a macOS GitHub Actions runner on every push/PR — this is the only build verification the iOS target gets short of an actual Mac.
- `scripts/fix-capacitor-spm-paths.mjs` (wired as `postcap:sync`) fixes `ios/App/CapApp-SPM/Package.swift`: `cap sync` writes local Swift package paths using the host OS's separator, and Windows backslashes there are not valid path separators for Swift Package Manager on macOS/Linux — every `cap sync` run on this machine would otherwise silently reintroduce a path Xcode/CI can't resolve.

**Keeping the two targets in parity**: don't branch app logic on platform by hand. The existing pattern (`src/utils/deviceBattery.ts`, `src/utils/share.ts`) is to call a `@capacitor/*` plugin unconditionally — each one detects the platform itself and either bridges to the real native API (iOS) or wraps the closest web equivalent, with a further graceful fallback (e.g. clipboard copy) when neither exists. Follow that shape for any new native-feeling feature instead of adding `Capacitor.isNativePlatform()` checks throughout feature code — it's what keeps the web build's behavior unchanged while the iOS build gets the real native API for free.

`capacitor.config.ts`'s `appId` (`com.guessbattery.app`) is a placeholder and must be replaced with a real reverse-DNS identifier before any App Store Connect record is created — it's effectively permanent once submitted.

The web build also carries a PWA manifest (`public/manifest.json`, `public/icons/`) and iOS-specific meta tags in `index.html` (`apple-touch-icon`, `apple-mobile-web-app-*`), so it can be "added to home screen" with a real icon on both Android and iOS Safari — the closest thing to an installed app for anyone using the web version before/without the native App Store release. `viewport-fit=cover` is also set there; `Navbar`/`BottomNav`/`StartCover` pad themselves with `env(safe-area-inset-*)` to compensate, for the native iOS shell's notch/Dynamic Island/home indicator (a no-op on the web, where those `env()` values just resolve to 0).

### App shell and mode switching (`src/App.tsx`)

`App.tsx` owns top-level flow state: splash screen -> start cover -> main game shell. Once past the cover, it renders exactly one of five game mode components based on `currentMode: GameMode` (`src/types/game.ts`), switched via `Navbar`/`BottomNav`:

- `single_5` -> `SinglePlayerGame` — solo run through 5 questions, filterable by category
- `daily` -> `DailyGame` — the Daily Challenge (see below); reached via `Navbar`'s menu or the `DailyChallengeBanner` shown above the mode content whenever `currentMode === 'single_5'`, not via `BottomNav` (its 4-tab grid was left alone rather than squeezed to 5)
- `mutual_pk` -> `MutualPkGame` — 1v1 realtime PK battle
- `party` -> `PartyModeGame` — pass-and-play, 2-4 players on one device
- `custom` -> `CustomCreator` — build/import/manage a custom question deck

All five are `React.lazy()`-loaded (each is its own chunk) so a player who only plays one mode doesn't download the others — notably, `MutualPkGame`'s chunk carries the entire Supabase client and is by far the largest (only loaded if PK mode is opened). `SplashLoader`, `StartCover`, and `DailyChallengeBanner` are the only components that must render on first paint (the banner needs to be visible without opening any mode), so they're imported eagerly; `StartCover` uses Framer Motion, which is why the main chunk still includes it regardless of which mode is picked.

Custom questions are persisted to `localStorage` (`guess_battery_custom_questions`) and merged with `INITIAL_QUESTIONS` (`src/data/questions.ts`) into `allAvailableQuestions`, passed down to every mode that needs a question pool.

### Internationalization (`src/i18n/`)

**DONE 2026-09-03**: added a full bilingual UI (Traditional Chinese / English) at the user's request, with automatic detection + a manual toggle — a lightweight custom setup, not a library like `react-i18next`, since the string surface is a fixed, known set rather than something that needs runtime-loaded locale bundles.

- `src/i18n/translations.ts` is the whole dictionary: a `zh` object (the source of truth) and an `en: Record<TranslationKey, string>` — `TranslationKey = keyof typeof zh`, so TypeScript hard-errors if `en` is ever missing a key `zh` has, instead of silently falling through at runtime. Values may contain `{token}` placeholders, filled by `interpolate()`/`t(key, vars)`. This file has **zero React dependency on purpose**: pure utility functions that need translated text but aren't components (`getCommentary`/`getDailyShareText`/`getBadgeTitle`/`getBadgeDescription` in `gameLogic.ts`, `getBotProfile` in `aiBots.ts`, `startMatchmaking`/`spawnBotMatch` in `matchmaking.ts`) import `translate(lang, key, vars)` directly and take an explicit `lang: Language = 'zh'` parameter — defaulting to `'zh'` is what keeps every pre-existing call site (and `gameLogic.test.ts`, which asserts on the default-Chinese output) working unchanged; English is opt-in via an explicit second/extra argument.
- `src/i18n/LanguageContext.tsx` is the only part that's React-specific: `LanguageProvider` (wraps `<App/>` in `main.tsx`) detects a first-time visitor's language from `navigator.languages`/`navigator.language` (anything not `zh-*` defaults to English — the point of the feature is a non-Chinese browser lands in English without hunting for a toggle), persists the resolved/chosen language to `localStorage` (`guess_battery_language`), and exposes `useLanguage()` returning `{ lang, setLang, toggleLang, t }`. The toggle itself is a small "EN"/"中" pill button in `Navbar`, next to the volume control — deliberately always shown in the *target* language's own script (an established convention for language switchers), not translated by `t()`.
- Every component that renders user-facing text calls `useLanguage()` and swaps literals for `t('key')`. Static UI chrome (buttons, labels, empty states, `alert()` copy) lives entirely in `translations.ts`; a handful of longer share-text templates (`GameOverModal`/`DailyGame`/`PartyModeGame`/`MutualPkGame`'s "share your result" strings) are also dictionary entries with placeholders rather than being built as JS template literals per language.
- **Built-in question content**: `Question` (`src/types/game.ts`) gained optional `titleEn`/`explanationEn` fields. All 140 built-in questions in `src/data/questions.ts` carry both — the English text was hand-translated (not machine-translated) sentence-by-sentence against the already-verified Chinese, so the underlying math/numbers never changed, only the wording; applied to the file via a one-off regex-based Node script (matched each `{ id, title, ..., category, emoji }` block by id and spliced the two new fields in) rather than by hand, to guarantee no id was missed or mismatched — the script asserted `140 of 140` blocks patched before writing. `getLocalizedQuestionText(question, lang)` in `gameLogic.ts` picks `titleEn`/`explanationEn` **independently per field** (not "both or neither") when present and `lang === 'en'`, falling back to the Chinese field otherwise — this matters for `MutualPkGame`'s real (human-authored) PK opponent questions, which get a localized `explanationEn` (the app's own boilerplate reveal note) but can never have a `titleEn` (nobody can auto-translate what a real opponent just typed). User-authored custom questions (`CustomCreator`) have no `*En` fields at all and simply render in whatever language the author wrote them, in either UI language — there's no way to auto-translate arbitrary player-authored text. `CATEGORY_LABELS` similarly gained `labelEn` per entry.
- `QuestionCard`'s keyword-highlighting (`formatTitle`) only runs for `lang === 'zh'` — its keyword list is hand-picked from the Chinese question titles' actual vocabulary, so English sessions just render the plain title unhighlighted rather than needing a parallel English keyword list. (While touching this list, also dropped a dozen-plus dead keywords left over from the removed `absurd` category — see Known issues below.)
- Bot identity (`aiBots.ts`'s `BOT_NAMES`) and the fallback opponent-question deck (`humanAiDeck.ts`'s `HUMAN_BOT_QUESTIONS`) both got English variants too, so a bot opponent's name and its questions localize along with everything else instead of staying Chinese-only inside an English session.
- Verified via `npx tsc --noEmit`, `npm run test` (42/42), `npm run lint`, `npm run build`, and an actual browser smoke test (dev server + Claude-in-Chrome): toggled EN -> confirmed every screen touched (start cover, navbar/menu, category pills, question card, slider, reveal screen with its localized explanation, footer) renders correctly, then toggled back to zh to confirm the round-trip.

### Scoring model

Every mode scores guesses the same way (`calculateScore` in `src/utils/gameLogic.ts`): `score = 100 - |guess - officialBattery|`, clamped at 0. `getCommentary`/`getCommentaryIcon` map the resulting distance to one of 8 flavor-text tiers; `getBadgeForScore` maps a session's average score to one of the `TITLE_BADGES` — deliberately based on `score` alone (see Combo below), so a lucky streak never inflates the title a player earns.

### Combo bonus (`getCurrentCombo`/`getComboBonus`/`getComboBonusSeries`, `src/utils/gameLogic.ts`)

`single_5` and `daily` (not Party or PK — see below) layer a combo system on top of the base score: a guess within `COMBO_HIT_DISTANCE` (15) of the official answer extends a streak; anything further breaks it back to 0. `getCurrentCombo` derives the current streak length purely from an `AnswerRecord[]` history's trailing `distance` values — no separate combo state — so `QuestionCard` (a live "連擊中" chip while answering) and `RevealScreen`/`GameOverModal` (the reveal celebration and the results breakdown/total) all compute it the same way from whatever `answers` they already have. `getComboBonus` pays nothing for a single hit (needs two in a row to feel like a streak), then +5 per hit beyond that, capped at +20. Not wired into `PartyModeGame`/`MutualPkGame` — a combo spanning different players' turns, or PK's single-question format, wouldn't mean the same thing.

**FIXED 2026-08-31**: `RevealScreen`'s combo sting originally had no sound function of its own — despite reading like it did in the feature's commit message, it re-triggered `playMatchFoundSound()` (PK matchmaking's "match found" sting) layered after the normal `playScoreSound()`. Gave it a real dedicated `playComboSound()` (`src/utils/audio.ts`, square-wave two-note rise, distinct timbre from the PK sting) so combo/PK sounds no longer share an identity.

### Daily Challenge & streak (`DailyGame.tsx`, `src/utils/dailyStreak.ts`)

`DailyGame` plays the same 5-question flow as `SinglePlayerGame`, but the questions come from `getDailyQuestions()`/`getDailySeed()` (`src/utils/gameLogic.ts`) — a deterministic shuffle seeded by today's date string, so every player sees the same 5 questions on the same day (Wordle-style). On completing it, `dailyStreak.ts`'s `recordDailyCompletion()` updates a `currentStreak`/`longestStreak` persisted to `localStorage` (`guess_battery_daily_streak`); `computeNextStreak`, the pure date-diffing core of that, is what's actually unit-tested (extends on the very next day, resets to 1 after any gap, is a no-op replaying the same day). The completed view adds a streak banner and a "分享今日戰績方格" button above the shared `GameOverModal`, building a Wordle-style emoji grid (`getResultEmoji`/`getDailyShareText`) rather than touching `GameOverModal` itself.

**FIXED 2026-08-31**: the daily seed and the streak's day boundary used to come from `new Date().toISOString().slice(0, 10)` — UTC, not local time — so a player east of UTC (this dev machine's zone included) would see "today" flip over at their local morning hours rather than at their midnight. Both now go through a shared `getLocalDateString()` (`src/utils/date.ts`, unit-tested), which reads the `Date`'s local calendar fields instead of formatting a UTC instant: `getDailySeed()`/`getDailyQuestions()` (`gameLogic.ts`) and `recordDailyCompletion()`/`hasPlayedToday()` (`dailyStreak.ts`) all default to it now, and `DailyGame.tsx` computes its own `todayStr` the same way before passing it down explicitly. `dailyStreak.ts`'s `yesterdayOf()` helper is deliberately unchanged — it does pure calendar arithmetic on an already-resolved `YYYY-MM-DD` string (add/subtract one day via `setUTCDate`), which never depended on real-world local vs. UTC time to begin with, only on the string it's handed.

### PK mode matchmaking (`src/utils/matchmaking.ts`)

`startMatchmaking(userId, playerName, onMatched)` joins the Supabase `matchmaking_queue` table, checks for an already-waiting opponent, otherwise opens a Realtime channel subscribed to its own queue row and waits up to `MATCHMAKING_TIMEOUT_MS` (8s, `src/constants/gameConfig.ts`) for someone to claim it. If nothing works out — timeout, Supabase not configured (`isSupabaseConfigured` in `src/utils/supabase.ts`), or any error — it falls back to `spawnBotMatch()`, a local bot opponent. Callers get back a `cancel()` closure to tear down the timer/subscription on unmount.

Claiming an opponent is guarded two ways against two players calling `startMatchmaking()` within the same instant: the claiming update is conditional on the target row still being `status='searching'` (`.select()`'d to confirm it actually took), and — the trickier case, since a symmetric race has each side claim the *other's* row rather than contending for the same one — only the side whose own row is the objectively *newer* of the pair (by server-assigned `created_at`, tie-broken by `id` — see `isNewer()`) ever attempts to claim; the older side always falls through to listen-and-wait instead. Both sides agree on this ordering independently since they're comparing the same server timestamps (and, on a tie, the same two ids), so exactly one side of any pair ever claims. **FIXED 2026-08-31**: the `id` tie-break didn't originally exist — the comparison was plain `opponentRow.created_at < inserted.created_at`, which is false on *both* sides when the two rows' `created_at` are bit-for-bit identical. Sounds unlikely, but reproduced directly while manually testing two simultaneous browser tabs against the real Supabase backend: both inserts landed with the exact same server timestamp down to the microsecond, so neither side ever claimed, and both burned the full `MATCHMAKING_TIMEOUT_MS` and fell back to separate bots despite both being real, waiting opponents for each other the whole time.

Bot opponents are deliberately made indistinguishable from real ones in the UI (`MutualPkGame.tsx` comments call this out explicitly) — `opponent.isBot`/`botDifficulty` only ever drive internal pacing and guess-error-margin logic (`utils/aiBots.ts`), never a UI "this is a bot" tell.

Real human-vs-human PK matches also sync the actual gameplay, not just matchmaking: once matched, both sides join a Supabase Realtime *broadcast* channel keyed by the match's `roomId` (`src/utils/pkRoomChannel.ts` — no schema/table needed beyond what matchmaking already sets up) and exchange their authored question and their guess directly. Plain broadcast has no message history for a late subscriber, so each side also broadcasts a `ready` event the moment its own subscription completes; a side that already sent something resends it on receiving a peer's `ready`, closing the race where a message is sent before the peer has finished joining. Generous timeouts (`PK_OPPONENT_QUESTION_TIMEOUT_MS`/`PK_OPPONENT_GUESS_TIMEOUT_MS`, `src/constants/gameConfig.ts`) fall back to a synthesized question/guess if the real opponent disappears mid-match, so a match can never hang forever. Bot matches are unaffected — they still fabricate both sides locally, same as before, since a bot has no real second party to sync with.

The "synthesized question" in both of those fallback cases (an actual bot match, or a real match's opponent-question timeout) is drawn from `src/utils/humanAiDeck.ts`'s `HUMAN_BOT_QUESTIONS` — a small fixed deck of pre-written human-sounding questions (`MutualPkGame.tsx`'s `fabricateOpponentQuestion`). The opponent's synthesized *guess*, and bot *identity* (name/avatar via `getBotProfile()`), both always go through `aiBots.ts` instead — so there is exactly one bot identity/guessing system (`aiBots.ts`), with `humanAiDeck.ts` scoped to fallback question content only. **FIXED 2026-08-31**: `humanAiDeck.ts` used to also export a second, unused identity/guessing system (`HUMAN_BOT_PROFILES` named/tiered personas, `generateHumanBotGuess()`) that nothing imported — dead code left over from an earlier design, since removed, so the file now only contains what's actually wired in.

The Supabase schema (`supabase/matchmaking_queue.sql`) is **not applied automatically** — it must be run manually in the Supabase SQL editor (table, RLS policies, and enabling the table on `supabase_realtime`) before matchmaking will find real opponents. Without `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` set (see `.env.example`), every PK match silently falls back to a bot.

**KNOWN ISSUE, confirmed 2026-08-31 — the "waiting" side of a real match never gets notified via Realtime, even when the DB shows it matched. MITIGATED 2026-09-05, root cause still not fixed.** Manually tested two simultaneous browser tabs (distinct guest ids) against the real Supabase project end to end: the *newer* side correctly found the older row, claimed it, and got `isBot=false` almost instantly — but the *older* (listening) side's `.channel(...).on('postgres_changes', ...)` subscription (step 3 above) never fired, and it burned the full `MATCHMAKING_TIMEOUT_MS` before falling back to a bot — this *despite* the claim having genuinely written `status='matched'`/`matched_with`/`room_id` onto its row (confirmed by re-querying the row directly via REST afterward). This also means the historical `matched` pairs in the table (e.g. from 2026-08-30) are **not** proof both real players actually got paired live — only that the claiming side's write succeeded. Root cause is unconfirmed but points at the `matchmaking_queue` table's Realtime delivery, not the client code (the subscription call itself matches `@supabase/supabase-js`'s documented v2 API, and `supabase.ts`'s client init doesn't disable anything) — check **Supabase Dashboard → Database → Replication** to confirm `matchmaking_queue` is actually toggled on under the `supabase_realtime` publication (re-running `supabase/matchmaking_queue.sql`'s `alter publication supabase_realtime add table matchmaking_queue;` line, idempotent, is the first thing to try) is still the right next step to actually root-cause this. **MITIGATED**: `startMatchmaking()` (`src/utils/matchmaking.ts`) now also polls its own queue row directly over REST (every ~1.5s, capped by `MATCHMAKING_TIMEOUT_MS`) alongside the `postgres_changes` subscription — `resolveMatchedRow()` is shared by both paths and `finish()` is idempotent, so whichever one notices the match first wins. This doesn't fix whatever is wrong with Realtime delivery on this table, but it means the listening side no longer depends on that delivery working to find its real opponent before the timeout. Not yet re-verified against two live browser tabs against the real Supabase project (only unit/type/lint/build-checked) — that manual two-tab test is what would actually confirm it. Also **FIXED 2026-09-05**: `fallbackToBot()`'s own cleanup update now guards on `.eq('status','searching')`, so a side that times out after having *already* been claimed by a real opponent no longer overwrites its own row from `matched` back to `cancelled`.

### Audio (`src/utils/audio.ts`)

All sound (BGM + SFX) is synthesized at runtime via the Web Audio API — no audio files. `withAudio`/`playTone`/`playNoteSequence` are shared plumbing: every effect function just describes an envelope/frequency shape and delegates scheduling to these. BGM runs on a `setInterval` arpeggiator and auto-pauses/resumes on `visibilitychange` so a backgrounded tab doesn't keep scheduling oscillators.

### Question data (`src/data/questions.ts`)

`INITIAL_QUESTIONS` is a large static array (`category: 'calculus' | 'geometry' | 'algebra' | 'mechanics' | 'economics' | 'finance' | 'custom'`). `CATEGORY_LABELS` maps category keys to their filter-pill label/icon — used by `SinglePlayerGame`'s category selector (a `grid-cols-3` grid, sized to comfortably wrap the 7-8 pills including `all`/`custom`). User-created questions get `custom_`-prefixed ids and/or `category: 'custom'`; several call sites check both (`q.category === 'custom' || q.id.startsWith('custom_')`) since imported/legacy custom decks may only satisfy one.

### Result sharing (`src/utils/share.ts`, `src/utils/shareCard.ts`, `src/constants/site.ts`)

**DONE 2026-09-04**: overhauled the "share your result" flow (`GameOverModal`/`DailyGame`/`PartyModeGame`/`MutualPkGame`'s share buttons) for social reach on Threads, at the user's request. Two gaps existed before this: none of the four share-text templates included a link back to the site, and `index.html` had no Open Graph/Twitter Card tags at all — a link posted or pasted anywhere unfurled as a bare blue link with no title/image, which is the single biggest lever for click-through on a share-first platform.

- **Site URL**: `src/constants/site.ts` exports `SITE_URL` (`https://guess-battery.vercel.app`) as the one place that domain lives. `getDailyShareText()` (`gameLogic.ts`) defaults its new `url` param to it; the other three share handlers pass `url: SITE_URL` explicitly into `t('share_*_text', {...})`. All four `share_*_text` dictionary entries (zh+en, `translations.ts`) now end with a `👉 {url}` line plus a couple of hashtags (`#猜電量 #GuessTheBattery`, English variants drop the Chinese tag) — anyone forgetting to pass `url` would leave a literal `{url}` in the shared text, since `interpolate()` doesn't error on an unmatched token, so every `t()` call site touching these keys must supply it.
- **Open Graph / Twitter Card** (`index.html`): added `og:title`/`og:description`/`og:image`/`og:url`/`twitter:card=summary_large_image` etc., pointing at `public/og-image.png` (a static 1200x630 PNG). That PNG is **not** built from the live app — it's rendered once by hand from `scripts/og-image/generate.html`, a standalone vanilla-JS/Canvas2D file with zero build step (see its header comment for the regenerate steps). It was actually produced during this session via Claude-in-Chrome: opened the file, read `canvas.toDataURL()` back out, and decoded it to `public/og-image.png` — there's no npm script for this, it's a manual one-off asset.
- **Visual share cards** (`src/utils/shareCard.ts`): every share button now also generates a branded 1080x1080 PNG "result card" (big stat, badge/result headline, stat chips, footer tagline+domain) via `renderShareCardImage(data)`, sharing Threads' image-first feed as intended rather than posting text-only. **This function is deliberately synchronous** (`canvas.toDataURL()` + a hand-rolled base64→Blob decode, not the async `canvas.toBlob()` callback, and no awaiting `document.fonts.ready`) — confirmed by hand during this session that even a single `await` between the click and the `navigator.share()` call is enough for Chrome to reject it with `NotAllowedError: Must be handling a user gesture to perform a share request`, so every call site invokes `renderShareCardImage()` synchronously right before `shareResult()` with no `await` in between.
- **`shareResult()`** (`share.ts`) grew an optional third `image?: Blob` param. `@capacitor/share`'s `files` option only accepts `file://` URIs on native and is silently ignored by its own web implementation, so the image path branches by platform: native writes the Blob to the `@capacitor/filesystem` Cache dir first (new dependency, synced into `ios/App` via `cap sync`) and passes that file URI to `Share.share({files:[uri]})`; web calls `navigator.share({files:[file]})` directly, bypassing Capacitor's wrapper. If neither is available (typical desktop browser), the image downloads via a plain `<a download>` click instead, and the outcome reported back is a new fourth `ShareOutcome`, `'downloaded'` (`share_downloaded` in `translations.ts`) — the four share buttons all show a `Download` icon and distinct copy for that state, alongside the pre-existing `'shared'`/`'copied'`/`'unavailable'`.
- **Testing caveat**: Claude-in-Chrome's automated browser rejects *every* `navigator.share()` call with `NotAllowedError: Permission denied` regardless of gesture timing — confirmed with a minimal isolated test button, so this is an environment/sandbox restriction on that specific automation tool, not a reachable bug in app code. It means the `navigator.share`-with-files path can only be exercised on a real device/browser (same caveat as PK mode's realtime sync — see Known Issues); testing through that tool alone will always fall through to the download+clipboard branch.
- **FIXED 2026-09-05**: `shareCard.ts`'s `wrapText()` (used to line-wrap `headline`/`subtitle` onto the card image) sliced its last line via `chars.slice(chars.indexOf(ch))` — `indexOf` finds the *first* occurrence of that character anywhere in the string, not the current loop position, so any text with a repeated character before the wrap point (e.g. the `balanced` badge's description, which repeats "偶爾", or a Party-mode champion list with a repeated name/avatar character) could re-emit already-shown text into the "last" line and truncate it early. Reproduced in isolation with a minimal harness before fixing (confirmed the bug, then confirmed the fix) — changed the slice to use the loop's own index `i` instead. Text-only shares were never affected, only the generated image.
